# Browser runtime notice audit

24 September 2026. The runtime component notice review is **complete for the
pinned artifacts**. This records the scoped source review and generated-output
verification; it does not close provider, hosting or overall publication gates.

## Artifact and source identity

The application serves five unmodified files from Pyodide 314.0.7. Their sizes
and SHA-256 hashes are pinned in `public-site/licenses/runtime-assets.json`.
The asset build verifies both installed inputs and copied output. Runtime metadata
identifies CPython 3.14.2 and Emscripten 5.0.3. Exact notice source URLs, hashes,
extraction rules and source-file inventories are in
`public-site/licenses/provenance.json`.

The pinned [Pyodide build flags](https://github.com/pyodide/pyodide/blob/314.0.7/Makefile.envs)
and [CPython dependency build](https://github.com/pyodide/pyodide/blob/314.0.7/cpython/Makefile)
identify the native dependencies. A Python builtin-module list alone does not
prove all linked dependencies or their notices.

## Verification and changes requiring review

The final generated-output check found all 43 collected runtime notice texts
byte-for-byte in THIRD-PARTY-NOTICES.txt (including original mixed newlines).
All notice files are included in the explicit source-release inventory. Both
installed and distributed copies of all five runtime assets match their pinned
SHA-256 hashes and sizes. The generated vendor inventory records the same
provenance plus six actual bundled JavaScript packages. The Pyodide and hiwire
source links are present in the distributed credits. Local evidence is recorded
in ignored output/diagnostics/runtime-notice-final-audit.json.

The build's nativeComponentAuditComplete flag applies to this reviewed runtime
and inventory. A runtime, source component, upstream patch or dependency change
requires reopening the affected review, updating provenance and repeating the
output checks. Integrity checks alone cannot establish new licence coverage.
Source availability and build instructions were inspected, not a full upstream
compiler rebuild. Optional/platform notices were included conservatively as
stated in the component table. These are limits of the evidence, not claims of
bit-for-bit reproducibility or an exhaustive binary linker map.

## SDL compatibility reference

The pinned [SDL JavaScript implementation](https://github.com/emscripten-core/emscripten/blob/5.0.3/src/lib/libsdl.js)
uses MIT. The pinned [SDL header](https://github.com/emscripten-core/emscripten/blob/5.0.3/system/include/SDL/SDL.h)
has a permissive copyright/permission notice; its separate API documentation
paragraph mentions LGPL. Both comments were preserved by the conservative scan.
The Pyodide build explicitly selects `-lsdl.js`, and the served JavaScript contains
SDL_Init, SDL_SetVideoMode and SDL_PollEvent implementations. Inspection of the
pinned WASM found no SDL-named imports and only one SDL-named export:
SDL_GL_GetProcAddress. The matching [Emscripten compatibility shim](https://github.com/emscripten-core/emscripten/blob/5.0.3/system/lib/gl/libprocaddr.c)
is MIT/NCSA code forwarding to emscripten_GetProcAddress. Its notice is included.

Together these support treating the distributed implementation as Emscripten's
compatibility code; the isolated documentation sentence is not evidence of a
linked native LGPL SDL library. This is an inference from the pinned build and
artifacts, not a general statement about all Emscripten/SDL configurations.
